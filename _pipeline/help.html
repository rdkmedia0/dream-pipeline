Dream Pipeline Help

A guide to running the AI video-generation pipeline: writing specs, generating videos, using the chat assistant, and fixing the most common issues.

Overview

Dream Pipeline turns a short concept into a rendered, uploadable video. Each video is identified by a number — what you call that unit (a "Dream," a "Tale," an "Episode," or anything else) is entirely up to your project's own naming, not fixed by the tool. For each number there's a spec (spec_NNN.json) describing what it is — title, premise, the actual prompt text, tags — which gets rendered through ComfyUI using a local Ollama model for any AI-composed writing.

Everything runs locally by default. Ollama hosts the language model, ComfyUI renders the video. The only optional exception is Gemini — if you save an API key in Settings, creative writing, vision QC, and/or keyframe generation can use Google's real API instead, at whatever per-role granularity you choose.

First run

  1. Start the web UI (the desktop shortcut, or python dream_step.py --web from _pipeline/).
  2. Open ⚙ Settings (top right) and confirm the Ollama and ComfyUI URLs point at your actual instances — defaults assume both are running on this machine.
  3. Click Refresh models from Ollama URL and pick a Creative model and Vision model from what's actually installed.
  4. Click Check dependencies to confirm your Ollama executable is found — if it's missing, install it before trying a real render. (ffmpeg isn't needed at all; ffprobe's job is done by the av Python package instead of a real ffprobe binary — neither is checked here since neither is an external dependency anymore.)
  5. Pick or create a project from the Projects screen, then go to Manage.

Core concepts

Projects

A project is a sibling folder of _pipeline/ (e.g. your channel's folder). Each project has its own specs, rendered videos, and concept list — projects never share content.

The field-locking rule

This is the single most important rule in the whole tool:

Any field you've typed content into is used exactly as-is, always. The AI never touches a field that already has content — even if you ask it to change the tone, style, or direction. If you want the AI to rewrite something, you must clear that field first.

Any field still blank is AI-composed automatically — no manual on/off switch, this is unconditional. Click Auto-generate missing content to fill in whatever's still blank across the selected rows; fields you've already typed stay exactly as they are.

Workflow types

TypeWhat it needsWhen to use it
t2v — text-to-video Just the prompt fields. Default. No reference image needed.
i2v — image-to-video One reference image. Renders from the same positive_prompt/ negative_prompt as every other workflow — since the image already fixes appearance, prefer describing the animation over re-describing appearance. You have a specific starting frame you want animated.
fml — first/middle/last Three reference images (or three keyframe prompts) for the opening, middle, and closing frames. A story with a clear beginning/turn/end you want to control precisely.

Custom workflow files

Each type (t2v/i2v/fml) is backed by a workflow_api_*.json ComfyUI graph. You can drop in your own exported graph alongside the built-ins instead of being limited to them:

  1. Export your graph from ComfyUI as an API-format JSON, and save it directly into the _pipeline folder as workflow_api_<anything>.json — the filename must contain t2v, i2v, or fml somewhere in it (case-insensitive), since that's the only way the pipeline can tell which type it's for.
  2. Open Settings → Workflow files. Your file appears in the matching type's dropdown, marked "(needs test)". Select it.
  3. The pipeline automatically detects which node holds the positive prompt, the negative prompt, and (for i2v/fml) the image input(s), using ComfyUI's own live node schema — the same technique Settings' model-file check uses, extended to trace prompt wiring through the graph. If it can't confidently identify these, it says so and you can't select the file until the graph is fixed or a different one is picked.
  4. Once detected, click Test this wiring. This runs a real render through ComfyUI with a placeholder prompt (and, for i2v/fml, a test image you supply) — it uses real GPU time, so only do this when you're ready to spend it.
  5. Review the result. If it looks right, confirm to save it — it becomes the active file for that type. If not, discard it; nothing is saved and you can try again.
The pipeline only wires up the parts it actually sends data into (prompts, images, seeds). Everything else in your graph — samplers, resolution, model choices, LoRAs — is used exactly as you exported it. You're responsible for the graph itself being correctly configured in ComfyUI; this only finds and confirms the handful of fields it needs to write into.

Manage table

This is where you write and edit spec content. Load number(s) with the field at the top (a single number, a range like 1-5, comma-separated, or all).

Running things

One button does double duty, depending on the selected rows:

  • Auto-generate missing content — shown while any selected row still has a blank field. Writes spec/keyframe content for those rows (fields already filled in stay exactly as-is). Never renders anything, and the table refreshes afterward so you can review the result.
  • Render video — shown once every selected row is fully filled in. The separate, explicit render step: renders for the first time, or re-renders (overwriting the current file) if one already exists. Always asks for confirmation.
  • Clear content — wipes spec content (and any staged reference images) for the selected rows back to blank, ready for a completely fresh generation. Never touches an already-rendered video.

Every cell with content has a small × button to clear just that field — useful when you want the AI to redo one specific field without touching the rest.

Need new ideas?

Dispatches a real web-search-capable agent to research what performs well in this genre, follow this project's own CREATIVE.md for tone and format, and append new entries to the master concept list.

Check Use performance trends to also feed in real YouTube Analytics data (top-performing titles/tags, and each top video's real premise/script excerpt when it's still local) — requires this project's Analytics to have been refreshed at least once. You can optionally include top performers from other projects too, and the AI is explicitly encouraged to creatively merge two well-performing concepts into one new idea when it genuinely fits.

Performance trends in spec/script generation

Separate from the idea-generation checkbox above: Settings → Creative writing → "Use performance trends when writing content" quietly applies the same kind of trend data to every AI-composed row (blank fields via the manage table, and the CLI's own generation), off by default. It's deliberately framed as style/word-choice signal only — it can never change or override a row's own locked title/premise — and safely no-ops with no error if this project has no analytics data yet. A second Settings sub-toggle controls whether it goes as deep as pulling real script excerpts from past renders still on disk, or stays at title/tags only.

The render pipeline

A render goes through ComfyUI using one of four workflow graphs (workflow_api_*.json in _pipeline/), each with its own fixed node layout. VRAM guard (vram_guard.py) automatically frees GPU memory held by a local model before a render starts, so Ollama and ComfyUI don't fight over the same GPU.

If a render fails right after switching a number to a new graph type, it's almost always because that type's extra fields (image, i2v/fml prompts) haven't been filled in yet — go back to Manage and fill them in, or just leave them blank and click Auto-generate missing content, which composes them automatically, then retry.

Video review

Rendered videos show up in the Videos sidebar tab, split into Active (needs review) and Reviewed. Selecting one plays it in the Player card, with Move to Reviewed and Delete underneath, plus its own Prev/Next controls and a Review mode toggle — all present whether or not you've entered true fullscreen (the Fullscreen button above the player just makes the whole player fill the screen; the controls themselves don't change).

Review mode & feedback

Toggling Review mode on shows a feedback box under the video — off by default so it doesn't take up space during ordinary viewing, and it stays on as you step through videos with Prev/Next so a review pass doesn't need re-enabling it each time.

Type what didn't work about the video and submit — the AI revises the existing story/prompt to address it (a real edit, not a fresh unrelated rewrite) and proposes a revision before anything renders. The proposal shows a plain-language summary of what it changed and why (e.g. "Since you mentioned the melon joke didn't land, I rewrote the second beat's dialogue and removed the melon prop entirely"), plus which model answered (e.g. gemini:gemini-3.1-flash). From there:

  • Accept — writes the revision and queues the render.
  • Try again — asks for a fresh attempt with the same feedback.
  • Refine — add more direction in the box below and regenerate with it folded in, if the first attempt was close but not quite right.

Once accepted, the render starts immediately if nothing else is currently rendering; otherwise it queues automatically and a status overlay on the video tracks progress, so you can keep reviewing other videos while it works in the background. Accepted reworks are rendered one at a time, in the order accepted, and never start while any other render is in progress — no need to wait for it yourself before reviewing the next video. The Manage tab's usual render-progress panel picks this up too, the same as any other render.

Chat assistant

A help chat lives in its own sidebar tab, next to Videos. It can answer questions about how the tool works, read/save Creative-tab fields and golden rules directly, list this project's videos, and — for numbers already loaded in the Manage table — propose spec field content. Deleting a video or starting a render always requires your own explicit Confirm click in the chat; nothing destructive or GPU-spending ever happens from a chat reply alone.

Reviewing spec-field proposals: when the assistant suggests spec field content for a Manage-table row, you'll see an Apply option. Clicking it fills the matching cells in the table — exactly as if you'd typed it yourself — but you still have to click Auto-generate missing content (or just save it as-is if every field is filled) afterward for anything to actually be saved.

Chat model

Chat uses your local Ollama model — including real web search, via a tool-calling loop that needs no account of any kind.

YouTube upload

Uploading needs a one-time OAuth "Desktop app" client, set up once in Settings under "YouTube credentials" — shared across every project. Each project then gets its own token.json, but its first upload reuses whatever session Settings' connection check already verified (or any other project's prior upload) automatically — no extra browser step for it. A real "Allow" click in a browser is only ever needed once overall, the very first time this app is authorized on this Google account at all (via Settings' "Save"/"Reauthorize", or a project's first upload if that hasn't happened yet) — this step can't be automated or skipped, but it never repeats after that.

Dependencies & migration

This pipeline runs end to end on ComfyUI + Ollama — nothing else is required. The "Check dependencies" button in Settings confirms both services' HTTP APIs actually respond at their configured URLs, which is the first thing worth checking after moving this pipeline to a new machine — there's no local-executable check of any kind, purely URL reachability, so it reports identically whether either service is local or on a completely different host. Neither ffmpeg nor ffprobe are needed anymore — ffmpeg's only caller (an experimental multi-shot rendering feature) was removed, and ffprobe's job is done by the av Python package instead of a subprocess call. VRAM guard (freeing GPU memory before a render) talks to Ollama and ComfyUI purely through their own HTTP APIs — no nvidia-smi or local process management involved — so this orchestrator no longer needs to run on the same machine as Ollama/ComfyUI/the GPU (e.g. this pipeline on Linux behind a Cloudflare tunnel, Ollama/ComfyUI/the GPU on a separate Windows box reachable over the network) — just point Ollama URL/ComfyUI URL at that host. One remaining piece isn't cross-host safe yet: i2v/fml2v reference-image handoff to ComfyUI is still a local file copy.

Python package requirements are listed in _pipeline/requirements.txt (pip install -r requirements.txt). The four workflow_api_*.json files must move together with the rest of _pipeline/ — they're referenced by fixed ComfyUI node IDs, so a re-export from ComfyUI on the new machine can silently break a workflow; the pipeline validates this at load time and will tell you exactly which node ID is missing if that happens.

Guided setup: python _pipeline/setup_installer.py walks through everything on a fresh machine — installs Python packages, optionally installs Ollama and ComfyUI (skip anything you already have), and downloads whatever model files are actually missing. Which files are needed is worked out live by reading the workflow_api_*.json graphs and confirming each candidate against ComfyUI's own running API — not a fixed list, so it stays correct if a workflow changes or a new one is added. Known files download automatically from their real, pre-verified HuggingFace sources (_pipeline/install_manifest.py); for anything without a pre-verified source, both the CLI and the web UI's Settings/dependency-check popup give you a one-click HuggingFace search by filename — most ComfyUI models can be found there — but you're responsible for confirming it's actually the right file (correct quantization/precision, not a tampered mirror) before placing it manually. It never re-downloads a file that's already present, and every step can be skipped. Scoped to Windows/Linux with an NVIDIA GPU — see the FAQ below for why AMD/Intel aren't covered.

Exposing Ollama/ComfyUI on your network

By default, both Ollama and ComfyUI only listen on localhost — fine when everything runs on one machine, but if this pipeline runs on a different machine (or in a container) than Ollama/ComfyUI/the GPU, each service needs telling to accept connections from other machines, and each machine's firewall needs a rule allowing it. Neither step is this pipeline's job — it only ever talks to whatever URL you put in Settings — so this is standard Ollama/ComfyUI/OS administration, covered here because getting it wrong is the single most common reason a correctly-typed URL still shows unreachable.

WindowsLinux
Bind beyond localhost Set the OLLAMA_HOST environment variable to 0.0.0.0 (System Properties → Environment Variables, or setx OLLAMA_HOST 0.0.0.0 in an admin terminal), then restart Ollama. For ComfyUI, launch with --listen 0.0.0.0. Same OLLAMA_HOST=0.0.0.0 (e.g. in the systemd unit's Environment= line, or exported before launching manually). Same ComfyUI --listen 0.0.0.0 flag.
Open the firewall port Windows Defender Firewall → Advanced settings → Inbound Rules → New Rule → Port → allow Ollama's (11434) and/or ComfyUI's (8000/8188) TCP port. Distro-dependent — e.g. sudo ufw allow 11434/tcp and sudo ufw allow 8188/tcp on Ubuntu, or the equivalent firewall-cmd/iptables rule elsewhere.

Binding a model-serving API to 0.0.0.0 and opening a firewall port makes it reachable by anything else on that network, with no authentication of its own — fine on a trusted home/LAN, worth a real second thought (a VPN, or at least router-level access rules) before doing this on anything more exposed. This is the same trust model this pipeline's own web UI already documents for itself (see the top of this page).

Once bound and the firewall rule is in place, point Settings' Ollama URL/ComfyUI URL at that machine's real LAN address (e.g. http://192.168.1.20:11434) instead of localhost, then use Settings' Check dependencies to confirm it's actually reachable from where this pipeline runs.

FAQ & troubleshooting

I asked the AI to change something but the result looks unchanged

This is almost always the field-locking rule: any field with existing content is used verbatim, regardless of what you type into AI direction. Clear the field(s) you want rewritten first (the × button on that cell), then click Auto-generate missing content again.

"Switching to <type> needs [...], not yet set"

Changing a number's graph type (e.g. t2v → i2v) requires that type's extra fields (an image, or i2v/fml-specific prompts) to already exist. Load that number into Manage, fill those fields in — or leave them blank — click Auto-generate missing content, then retry the render.

A render fails with a missing-node-ID error

The named workflow_api_*.json file was likely re-exported from ComfyUI (even a routine resave) and its internal node IDs shifted. Either restore the previously-working file, or re-run the conversion (convert_workflow_to_api.py) on a fresh export and update the matching entry in generate_dream.py's WORKFLOWS dict with the new IDs.

Check dependencies reports something MISSING

Install the named tool and make sure it's on your system PATH, then re-run the check. The checked tool (Ollama) works the same way on Windows and Linux, so this check isn't platform-dependent.

Can I move this pipeline to another machine?

Yes — see Dependencies & migration above. Copy the whole _pipeline/ folder plus your project folders, install the pip requirements, point Settings at wherever Ollama/ComfyUI run on the new machine, and run "Check dependencies" to confirm everything's in place.

What does the AI chat actually have access to?

It can read this project's spec content, Creative-tab fields, and golden rules, and save changes directly to the latter two (reversible by editing again, same as any other saved content). It can also list this project's videos. For a Manage-table row, it can only ever propose spec field content — that needs an explicit Apply click from you, then Auto-generate missing content/render as normal to actually save it. Deleting a video or starting a render always requires its own separate explicit Confirm click in the chat itself; nothing destructive or GPU-spending happens from a chat reply alone.
